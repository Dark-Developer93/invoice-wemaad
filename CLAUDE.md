# CLAUDE.md

Guidance for Claude Code (and future contributors) working in this repo. This
file documents the *patterns* the codebase follows and the *why* behind
non-obvious decisions, so new features can be added consistently instead of
each one inventing its own approach.

## Stack

- Next.js 15 (App Router, Server Actions, Turbopack dev), React 19
- Auth.js v5 (`next-auth@beta`) with the **database session strategy**
  (`Session` table via `@auth/prisma-adapter`) — not JWT
- Prisma 6 + PostgreSQL (Neon, free tier, region `eu-central-1`)
- Zod for all validation (env vars, forms, server action input)
- Conform (`@conform-to/react` + `@conform-to/zod`) for form state
- Tailwind + shadcn/ui (Radix primitives) for UI
- Vitest for unit tests
- React Email + `@react-pdf/renderer` for emails and invoice PDFs
- Deployed on Vercel, pinned to region `fra1` (closest to the Neon DB)

## Core patterns

### 1. Server actions follow one shape

Every mutating action in `app/actions/*.ts` follows:

```
"use server";
1. Resolve identity: getRequiredUserId() / requireUser() / requireAdmin()
2. Validate input with Zod (parseWithZod for form actions, schema.parse
   for programmatic ones)
3. Mutate via Prisma, scoped to the caller's userId in the WHERE clause
   (never trust a client-supplied ownership check alone)
4. Invalidate: revalidateTag(cacheTags.X(userId)) for anything cached,
   revalidatePath(...) for anything not using the tag cache
5. Return a typed result ({ success: true } / { error: string } /
   a Conform SubmissionResult for form actions)
```

Follow this shape for any new action. Auth check is always first — never
validate or touch the DB before confirming who's calling.

### 2. Ownership is enforced in the query, not just checked before it

Prefer `prisma.invoice.update({ where: { id, userId } })` (composite,
atomic) over `findUnique` + ownership `if` + separate `update`. The atomic
form closes TOCTOU windows and gives you `result.count === 0` as a single
signal for "not found or not yours."

### 3. Concurrency-sensitive counters use a Postgres advisory lock

`getUserUsage` (invoice/email monthly limits) is deliberately **never
cached** — it must always reflect the true current count. Anywhere a
usage limit is checked and then acted on (`createInvoice`,
`processRecurringInvoices`), the check and the write happen inside the same
`prisma.$transaction`, serialized per user with:

```ts
await tx.$executeRaw`SELECT pg_advisory_xact_lock(hashtext(${userId}))`;
```

This closes the race where two concurrent requests both read "4 of 5 used"
and both proceed. The lock releases automatically at transaction end. Copy
this pattern for any new "check a limit, then create a row" flow — do not
add a plain `if (count >= limit)` before a separate `create()` call.

### 4. Caching: tag-based, invalidation-driven, zero TTL

Read-heavy queries are wrapped in `unstable_cache()` (Next.js Data Cache,
persists across requests — different from `React.cache()`, which only
dedupes within one request and is used for `auth()`). Rules:

- **Tag names live in `lib/cache.ts` only.** Every cache call and every
  `revalidateTag` call imports from there — never inline a tag string.
  Tags are always `` `${resource}-${userId}` ``, generated by a function so
  they can't be typo'd independently in two places.
- **No time-based expiry.** The only exception is the dashboard chart-data
  query, which buckets its cache key by UTC day because the query window
  itself is relative to "now" — that's an inherent property of the data,
  not a staleness tradeoff.
- **Every mutation of cached data must revalidate the matching tag(s) for
  the affected user** — including background jobs (the recurring-invoice
  cron, system alert emails) and **admin actions that mutate a target
  user's data**, where the tag must use the *target's* userId, not the
  acting admin's. Look at `app/actions/admin.ts` for the reference example
  before adding a new admin mutation.
- **Date fields need manual normalization at the cache boundary.**
  `unstable_cache` serializes its return value, so `Date` objects come
  back as ISO strings on a cache hit. Any cached function whose result is
  later used with `Date` methods (`.toLocaleDateString()`, `date-fns`,
  etc.) must re-wrap those fields with `new Date(x)` before returning
  (`new Date()` on an already-real `Date` is a no-op, so this is safe on
  both hit and miss). Check each new cached query's consumers before
  deciding whether normalization is needed — don't apply it reflexively.
- Session validation is **not** part of this cache. Auth.js uses the
  database session strategy, so every request still does one session
  lookup regardless of data-cache hits; `React.cache()` on `auth()` only
  removes *duplicate* lookups within a single request/render pass.

When adding a new read-heavy query: pick (or add) a tag in `lib/cache.ts`,
wrap the query in `unstable_cache(fn, [cacheKeyParts], { tags: [...] })`,
and grep every action that writes to that model to make sure each one
calls `revalidateTag` with the same tag.

### 5. Rate limiting is best-effort, not a hard guarantee

`lib/rateLimit.ts` is in-memory per server instance — it resets on cold
start and doesn't share state across concurrent serverless instances. It's
a first line of defense against casual abuse (magic-link mail-bombing,
contact-form spam), not airtight enforcement. If stronger guarantees are
ever needed, replace the backing store with something shared (e.g. Redis /
Upstash) rather than adding TTL logic on top of the in-memory map.

### 6. Middleware is defense-in-depth, not the auth boundary

`middleware.ts` runs on the Edge runtime and can only check for the
*presence* of a session cookie (Auth.js's database strategy needs a real
DB round-trip, which isn't Edge-safe). Real authorization — validating the
session and checking `isActive`/`isAdmin` — happens in
`app/dashboard/layout.tsx` / `app/admin/layout.tsx` via
`requireUser()`/`requireAdmin()`. Every new protected route still needs
its own `requireUser()`/`requireAdmin()` call; don't rely on the
middleware matcher alone (that gap is exactly how the invoice-PDF route
was once left unauthenticated).

### 7. Env access is centralized and validated

Never read `process.env.X` directly in app code. Add the variable to the
Zod schema in `lib/env.ts` and read it via `env.X` (or `getEnv()`). This
keeps a missing/malformed env var a single clear startup error instead of
an undefined-value bug three layers deep. `env` is a lazy singleton
(parsed on first access) specifically so `next build`'s static analysis
doesn't require production env vars to be present.

### 8. Cron jobs record their own run history

Any new scheduled job (`vercel.json` → `crons`) should call
`recordCronRun()` (`lib/monitoring.ts`) with start/end time and
processed/failed counts, and `alertAdmins()` on unexpected failure. This
is what backs `/admin/monitoring` and `/api/health` — without it, a
silently-failing cron is invisible until a user complains.

## Testing

- `npm run test` — Vitest, currently 65 tests, all in `__tests__` folders
  next to the code they cover.
- When mocking `next/cache` in a test, mock **both** `revalidatePath` and
  `revalidateTag` — an action that calls the one you didn't mock will
  throw "Invariant: static generation store missing."
- `npx tsc --noEmit` and `npm run lint` should both be clean before
  committing.
- No E2E/browser test suite exists yet. UI changes and cache-invalidation
  behavior have so far been verified manually (Playwright driven ad hoc,
  plus direct Postgres query-log inspection) rather than via a committed
  automated E2E suite — see "Known limitations" below.

## Known limitations (surfaced by audits, not yet addressed)

These are conscious tradeoffs or deferred work, not oversights — listed
here so they're not rediscovered from scratch:

- **Rate limiting doesn't survive multi-instance/serverless scale-out**
  (see pattern 5). Fine for current traffic; revisit with a shared store
  if abuse becomes a real problem.
- **No E2E test suite.** Unit/action tests are solid (65 passing), but
  there's no committed browser-driven regression suite — UI regressions
  currently rely on manual testing before merge.
- **No data retention/pruning job.** `EmailLog`, `Notification`, and
  `CronRun` rows accumulate indefinitely. On Neon's free tier (0.5 GB
  storage cap) this is worth revisiting once real usage data exists (see
  the capacity note below).
- **Single-region deployment**, no multi-region failover — acceptable at
  current scale, matches the single-region Neon free-tier database.
- **No external alerting integration** (PagerDuty/Slack/etc.) —
  `alertAdmins()` currently only does in-app notification + email. If both
  channels are down or unwatched, an admin won't be paged.
- **Neon free-tier capacity is untested against real traffic.** The 100
  CU-hour/month compute budget is sensitive to *request cadence*, not just
  user count — see the capacity discussion the team has separately for the
  reasoning and the plan for watching actual usage via Neon's dashboard
  once live.

## Common pitfalls when extending this codebase

- Adding a new cached query without adding its invalidation call in every
  action that mutates the underlying model (including admin actions and
  background jobs).
- Adding a `revalidateTag` call using the acting user's id instead of the
  target user's id in an admin action.
- Checking a plan/usage limit outside the same transaction as the write it
  gates (reintroduces the TOCTOU race pattern 3 exists to prevent).
- Reading `process.env` directly instead of going through `lib/env.ts`.
- Bypassing the WHERE-clause ownership pattern (pattern 2) with a
  find-then-check-then-mutate sequence.
